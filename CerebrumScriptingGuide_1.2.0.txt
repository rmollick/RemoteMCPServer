Overview


Cerebrum is the GameManager/ObjectMessageHandler/LevelGenerator package which manages dynamic level generation, scenario logic, and scene intelligence. It is currently under development so the syntax and grammar are changing as it grows.  


Why Cerebrum?
The goal of Cerebrum is to make reusable components which are external to the game application/executable, so that changes to an existing simulation or creation of new simulations or variations can be quickly and easily made.  Goals and benefits include:
* Most of game is dynamic through extensive use of StreamingAssets
* Logic and scenes can be changed without game rebuilds
* Existing C# routines can be simply and quickly integrated for complex behaviors
* Assets/scenes can be dynamically loaded/created at runtime.
* Assets can be dynamically changed/updated at any time.
* Can co-exist/work-with existing projects/code.
* New commands can be easily added to the language through Message Handlers.
* Variable and expressions support permits easy reference of GameObjects
* Supports logic, loops, variables, expressions, and psuedo-arrays (dictionaries)
* Short-hand name access for finding GameObjects in a hierarchy.


In Cerebrum, scripts are called Scenarios and are stored in Scenario Files.  With Cerebrum, your game world can be modified simply by changing variables in external Scenario files.  For example, the following scenario file Bed2.txt defines variables associated with Bed #2:

In Cerebrum, scripts are called Scenarios and are stored in Scenario Files located under the Assets/StreamingAssets folder.  These files have a .txt extension.

Scenario File scripts handle variables and logic, and pass commands to the GameObjects in a scene for them to do certain things, like move, play animations or sounds, get input, or custom complex behaviors.




Game Manager
Cerebrum’s GameManager (GM) parses the Scenario File(s) and handles certain commands and statements, logic and flow, as well as evaluating expressions and variables.  MyGameManager is the base class which handles the processing of the scenario files.  GameManager extends it to support Unity’s Addressables system for having modular scene/environment assets.


Any commands not handled by it are assumed to be for another Unity GameObject (GO), and the GM tries to identify the named GO and pass the command string to it.  Commands (in bold) include:
* $Cart moveTo $newPosition
* $Patient speak “Hello”
* $Nurse grab $KidneyDish
where the $ are varaibles referencing Unity GameObjects (GOs).

Object Message Handlers
All Unity GameObjects can receive Cerebrum commands through Message Handler components (MH), which act like native functions.  If a GameObject doesn’t have a message handler component, the GameManager will add the default ObjectMessageHandlerBase to it so it can receive messages. The GO’s ObjectMessageHandler (OMH) is a component which can inherit from the ObjectMessageHandlerBase component (OMHB).  The OMHB understands built-in commands such as moveTo, rotateY , etc.  The OMH adds additional commands and can be modified by the developer.  Any OMH class that inherits the OMHB will be called if the OMHB does not recognize one of the commands, which allows the developer to add arbitrary commands to the language.  In addition, the developer can directly inherit from the OMHB class to make their own MessageHandler compoents to extend the language through adding a HandleMessagefunction.  To add support for telling GameObjects to spin around a number of times over a period of seconds:
Chair SpinAround 5 3  #have the chair object spin 5 times over 3 seconds

we could add the command SpinAround to the OMH’s HandleMessage function:


    public override bool HandleMessage(string msg, string param, out string retString)
        if (msg=="spinaround")
        {
            //parse the parameters and execute the spin


Note: All keywords/commands in the GM and OMHB are NOT case-sensitive and are changed to lowercase before HandleMessage is called.


IMPORTANT: All parameters come in as one param string, so the developer must split and parse this string if it contains multiple parameters.  Each parameter should also be evaluated as it may be an expression, variable, number, or string.


Another example of this is the VitalsMH.cs component which handles commands sent to the VitalsMonitor.  It’s message handler supports the handling of one message called “setVitals” which sets 4 parameters (heart rate, pulseOx, blood pressure, and respiratory rate) on the in-game vitals monitor:

    public override bool HandleMessage(string msg, string param, out string retString)
    {
        retString = null;
        bool retv = base.HandleMessage(msg,param,out retString);
        if (commandFound)
            return retv;
       if (msg == "setvitals"){
            char[] separators = new char[] { ' ','\t'};


            string[] temp = param.Split(separators, StringSplitOptions.RemoveEmptyEntries);
            if (temp.Length > 0){
                param = temp[0];
                if (param != null && param[0] == '$') 
                    param =  ep.EvaluateParam(param);
                HRate = int.Parse(param);
                HRateText.text = param;
            }
            if (temp.Length > 1){
                param = temp[1];
                if (param != null && param[0] == '$') 
                    param =  ep.EvaluateParam(param);
                SpO2 = int.Parse(param);
                SpO2Text.text = param;
            }
            if (temp.Length > 2){
                param = temp[2];
                if (param != null && param[0] == '$') 
                    param =  ep.EvaluateParam(param);
                Pressure = param;
                PressureText.text = param;
            }
            if (temp.Length > 3){
                param = temp[3];
                if (param != null && param[0] == '$') 
                    param =  ep.EvaluateParam(param);
                RespRate = int.Parse(param);
                RespRateText.text = param;
            }


            heartRateMonitor.BeatsPerMinute = HRate;
            return true;
        }
        return false;
    }

RoomGenerator

In Cerebrun scenes, there is a RoomGenerator which uses Unity Addressables (https://docs.unity3d.com/Manual/com.unity.addressables.html)
to dynamically create levels, as well as reference GameObjects by their Addressables’ name.  


The RoomGenerator also can launch and support multiple GameManagers which run concurrently.  This can be used to have GameManagers running independently to monitor/manage individual characters such as multiple patients, with each patient running its own copy of the scenario files, and therefore having its own local copy of variables.  The RoomGenerator is beyond the scope of this guide and has its own guide, the Cerebrum Level Generator Guide.  In addition, the Cerebrum Addressables Guide is a companion which discusses Unity’s Addressables system.

Scenario Files 


Scenario files are text files which contain GameManager statements/expressions, and also commands for GameObjects (which are handled by their ObjectMessageHandler component).  Statements are either recognizable by the GameManager, or they are assumed to be commands for a GameObject which as an OMH component attached.  GameObject commands operate on a Noun-Verb-Modifier syntax (Subject-Command-Parameters).  Commands for the GameManager itself can omit an optional GM subject (usually omitted for clarity).  Commands and variable names are case-insensitive.  


Each Scenario file can be considered as its own function.  Scenario files are executed sequentially by the GameManager, and can call other Scenario files as subroutines using the Do command.  A scenario file will return to the calling file when it reaches the end of the file or when it encounters a Return statement.


Here are some examples of Scenario commands:


        GM wait 0.5                       #pause for ½ second with optional GM Subject
               Wait 0.5                              #pause for ½ second with GM Subject omitted


        #Setup Variables
        $Cup = ‘CupObject’                            #Unity GameObject named CupObject
        $PatientHand = Patient + ‘/LeftHand’         #Patient GameObject’s left hand child object


        #Have patient grab a cup with left hand
        $Patient grabLeft $Cup                    #move left hand to grab the cup object
        Wait 1                                    #wait for hand to move to cup
        $Cup attachTo $PatientHand            #attach cup to hand
        
        # If a button is pressed, pop up a message and do something 
        $ButtonPressed =                          #multi-line assignment when value is GO result
                ButtonObject isPressed   #GameObject command returns value


        Label ‘Loop1’                            #used for jumps and loops
        If
                $ButtonPressed
        Then
                Do ‘DoSomething.txt’         #call another scenario file (subroutine)
                Prompt ‘Did something.’    #pop up a message to the player screen
        Else
                Wait 0.1   #slow down loop
                Endif
        Goto ‘Loop1’

Scenarios as Functions


As of Cerebrum 1.1, Scenario files are now treated more like functions.  They can be called by their name with no file extension, can be passed optional parameters in the Do call, and can return a value.


Do call


The “.txt” file extension can now be left off the Scenario call:


Do 'EWS_Nurse/PatientCreations/Expressions/Smile' 
instead of 
Do 'NEWS_Nurse/PatientCreations/Expressions/Smile.txt'




Do Parameters


All scenarios can take optional parameters in the Do call to the scenario. These parameters get assigned to variables $param_1, $param_2, etc. or can be accessed by array notation $param[1], $param[2]. As these are global, and there can be nested Do calls, you should immediately assign them to other variables at the top of the scenario file, e.g. the PourPackage.txt file:


# Called by:
# Do 'PourPackage' $Package $Target $Height


If
        $param[0] > 0
Then
        $Package = param[1]
        $Target = param[2]
        $Height = param[3]
Endif
#Do stuff with $Package, $Target, and $Height…


IMPORTANT: parameter numbering starts at 1, NOT 0 as in C# arrays.  $param[0] is a special param that holds the number of parameters (not including itself).  So if param[0]==3, param[3] is the last parameter.

Unload Command


As seen above, an Unload command was added to clear the text cache of the scenario files, mostly for debugging purposes.  Normally, once a file is read in, it stays in cache so the file does not need to be read in again.  The Unload command makes sure that the next time it is called, the file is read in again (for if you want to dynamically make a change to the file while the simulation is running), e.g.:


Unload 'CerebrumTests/DoReturnTest'    #unloads Scenario if file needs to be changed

ObjectMessageHandlers


All GameObjects that want to be callable by a scenario file must have an ObjectMessageHandler component.  This can be from the ObjectMessageHandlerBase class, the ObjectMessageHandler class, or a class that inherits either of those. 


GameObject commands operate on a Noun-Verb-Modifier syntax.  
ObjectMessageHandlerBase (OMHB) commands:


Unity GameObjects can be identified by their Unity hierarchy or 2-levels of addressable names, or combinations of the two.  Cerebrum also supports abbreviated hierarchy path names as well.  The following are the types of names that can be used to access Unity GameObjects.:
* GameObject name or full name in hierarchy, e.g.
   * Player
   * /Table/Top
   * /metarig/spine/spine.001/spine.002/spine.003/spine.004
* Abbrieviated Hierarchy Name* (root name and some descendent)
   * /metarig/spine.004  (omits spine.001/spine.002/spine.003)
* AddressableName+ Abbrieviated Hierarchy (up to 2 levels of addressables) 
   * Bed1/Patient/spine.004
* Variable - e.g.: 
   * $PatientFace
* Expression (with no spaces!)
   * $Patient+'/metarig/spine/spine.001/spine.002/spine.003/spine.004'




*  The GM object lookup can find full path names both with the Addressables and without. For example, it will try to walk a hierarchy, but you can shortcut by eliminating children in between the root and the end object name. e.g. ’metarig/spine/spine.001/spine.002/spine.003/spine.004/spine.005/spine.006/Hair’ can be shorted to 'metarig/spine/Hair' or 'metarig/Hair'  You just need enough to differentiate between different clones. The GM can give unique names to the addressable instance clones by setting the RoomGenerator flag RenameObjects to true. Instead of all being Bed(Clone), the Addressable name/number is appended with the object name as follows: locName + locNum + "_" + objectAddressableName  which results in Bed4_PatientBedClickable

Expressions


Expressions and variables are denoted by a starting $
Only one $ needs to start an expression, so variables in the expression do not need a $.  The $ signals that what follows gets passed to the GameManager’s Expression Parser for evaluation.  




IMPORTANT:  All variables are GLOBAL within a single GameManager!  However, they are local to the GameManager when you have multiple GameManagers.


Expressions roughly follow the syntax of MS DataTable expressions:
https://docs.microsoft.com/en-us/dotnet/api/system.data.datacolumn.expression?view=net-5.0


NOTE: Prompt and = (assignment) statements assume expression follows, so no $ is needed
NOTE: Special =$ operator evaluates the result of the right-hand expression twice.
NOTE: Cerebrum uses spaces as separators, so in cases where multiple parameters or a single object name are expected, either use a variable or an expression which has NO WHITE SPACE.
NOTE: DataTable expressions use single = in expression for conditionals.  Cerebrum supports either singe = or double ==. e.g. $bool1 = (result = expected) or $bool1 = (result == expected)




$str1 = 'foo'
$bool1 = true
Prompt 'Check Convert function (bool to string)'
Prompt 'Result = ' + Convert(bool1 = true, 'System.String') + str1
Prompt 'Check IIF function'
Prompt IIF(bool1 = false, 'Bool1 is false:FAIL','Bool1 is true:PASS')
$bar = bar + 1                        #note the 2nd bar does not need a $ 
$choice = 2
$fileName = 'fileName'
$fileName1 = 'CheckPatient.txt'
$fileName2 = CheckSignature.txt'
$choiceFile =$ fileName + choice   #evaluated twice => ‘fileName2’ => ‘CheckSignature.txt’
$bool1 = (bool1 = false)        #note single = in expression for conditional, not assignment 
$objName = ‘Nurse’
$objName outline.on
$objName+’2’ outline.off

Assignment Variable Operator $$
The assignment variable operator $$ evaluates the left-hand variable as string and then treats that as a variable name to evaluate.


So:
                $StageTime = 2
                $taskName = 'TaskInfusionSqueeze' + StageTime
                $$taskName = taskNum
Is the same as:
                TaskInfusionSqueeze2= taskNum 
Assignment Eval Operator =$
The assignment eval operator evaluates the expression to a string and then treats that as a variable name to evaluate.


So:
                $StageTime = 2
                $taskName = 'TaskInfusionSqueeze' + StageTime
                $taskNum =$ taskName
                Prompt ‘taskNum variable is ‘ + taskNum


Is the same as:
                $TaskInfusionSqueeze2 = 5
                $taskNum = TaskInfusionSqueeze2
                Prompt ‘taskNum variable is ‘ + taskNum


Both will print the following:
taskNum variable is 5

Arrays
Cerebrum does not have true arrays where values are contained in a sequential block of memory.  Rather, it has pseudo-arrays where associated variable names are used to reference related data, and the =$ and $$ operators are used for building up and referencing variable names through string manipulation.  Pseudo-arrays can also be referenced and treated like arrays or dictionaries using the bracket notation [ ].  


Pseudo-Arrays


Note the use of pseudo-array $fileName to do similar function of DoChoice:
$fileName = 'fileName_'

$fileName_3 = 'CheckPatient3.txt'
$fileName_4 = 'CheckPatient4.txt'
$fileName_5 = 'CheckPatient5.txt'

Bracket Array/Dictionary Notation


Array and Dictionary notation is actually syntactic-sugar for the pseudo-arrays that evaluates the index between the brackets, and then appends that to the array name to make a new variable name, with an underscore in between.  e.g.:


$bar=5 
foo[bar] # becomes variable named foo_5 


$bar = 'hello' 
foo[bar]  # becomes a variable names foo_hello

Global Variable Manager


In order to coordinate multiple GMs running at once which each contain variables local to each GM, global variables can be used.  Global variables are shared among multiple GameManagers by having a GlobalVariableManager GameObject which has an Object Message Handler component OMHGlobalVariable.cs.  This MH understands two commands, setGlobal and getGlobal:


    public override bool HandleMessage(string msg, string param, out string retString)
    {


        . . .

        switch (msg)
        {
            case "setglobal":
                variables.AddSafe(varname,varvalue);
                break;
            
            case "getglobal":
            
                string theValue;
                if (!variables.ContainsKey(varname))
                    theValue = "0";
                else
                    theValue = variables[varname];
                retString = "'"+ theValue + "'"; //need to make into string expression
                break;

ObjectMessageHandlerBase commands:


Cerebrum can talk to any Unity 3D Game Object (GO) by passing a message to the named GO as an action or verb command.  This subject-command-parameters format takes the form of:


   Subject  Command [Parameter1] [Parameter2] etc 


where Subject is the GameObject, Command is an action, and there zero or more space-delimited parameter strings which depend on the command.

All Unity Game Objects (GOs) will have the ObjectMessageHandler based class (OMHB) added by default as a component if a Cerebrum Scenario File tries to pass a message to that GO, and all new ObjectMessageHandler classes (OMHs) inherit from this class and should call its HandleMessage base function if they don’t recognize a command.  

The commands all GOs (Object) will recognize are:


Object follow targetObject        #rigid body follow target
Object jump                                         #rigid body jump
NOTE: The jump command is a holdover from early testing of the system.  It isn’t really meant to be used.  It basically applies a force to the object if it has a RigidBody on it.

Custom ObjectMessageHandlers (OMHs)


In order to extend Cerebrum functionality by adding your own Object commands, your script should inherit from the ObjectMessageHandlerBase class (or the ObjectMessageHandler class) and implement the HandleMessage override member function.  You need to use the Cerebrum namespace.


using Cerebrum;


public class OMHChatBubble : ObjectMessageHandlerBase {


    public override bool HandleMessage(string msg, string param, out string retString)
    {
        retString = null;
        bool retv = base.HandleMessage(msg,param,out retString);
        if (commandFound)
            return retv;


        //OMHB doesn't return the evaluated parameter just in case you need to do something funky with it.
        if (param != null && param[0] == '$') 
            param =  ep.EvaluateParam(param);


        /*  COMMANDS */
        switch (msg)  //commands are all lower-case
        { 
        
     //Object setColor r g b
             “setcolor”:
            {
                //Color c;
                char[] separators = new char[] { ' ','\t'};
                string[] temp = param.Split(separators, StringSplitOptions.RemoveEmptyEntries);
                bubbleColor1[0] = float.Parse(temp[0]);
                bubbleColor1[1] = float.Parse(temp[1]);
                bubbleColor1[2] = float.Parse(temp[2]);
                backgroundSpriteRenderer.color = bubbleColor1;


                break;
            }
                /*MORE COMMANDS HERE*/
        }
        return true;
    }
When writing a message handler, you can either have the base HandleMessage function called prior to yours,  or if you want to replace existing commands, process your messages first and then call the base class:


bool retv = base.HandleMessage(msg,param,out retString);


When parameters are passed in to the GameObject, they come passed as one string, and therefore need to be split up and variables and expressions need to be evaluated.  Therefore, you will see:
char[] separators = new char[] { ' ','\t'};
string[] temp = param.Split(separators, StringSplitOptions.RemoveEmptyEntries);


to split the parameter string into individual parameters.  


Anytime a parameter may be a variable or expression, it needs to be evaluated by the expression parser ep by calling its EvaluateParam function:


        if (param != null && param[0] == '$') 
            param =  ep.EvaluateParam(param);


Many times this is called if the first character is a $ to denote a variable or expression is following, or by the character being a digit or negative sign or a single-quote denoting a string.


GetEvaluatedParameters


As of Cerebrum 1.1, ObjectMessageHandlerBase now has a new function, GetEvaluatedParams which will separate out the param string and evaluate each of the parameters separately, returning them in the out parameters:


        string [] parameters;
        GetEvaluatedParams(param, out parameters);
